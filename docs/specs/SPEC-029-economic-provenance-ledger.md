# SPEC-029 — Economic Provenance Ledger (Draft)

## Status

`APPROVED DESIGN — implementation not authorized`

## Purpose

Define a future capability for independently auditable economic effects created by new gameplay actions.

This specification exists because historical systems may not contain enough immutable economic provenance to reconstruct every past action safely.

## Relationship with TASK-130 / SPEC-026

This specification is complementary, not corrective.

It does not:

- change SPEC-026 evidence requirements;
- close historical H4 attempted captures;
- close historical H5 orphan commands;
- generate retroactive economic receipts;
- reinterpret mutable Inventory state as historical proof.

TASK-130 remains the owner of historical compatibility behavior.

## Proposed invariant

Every future economic mutation that opts into this capability should produce an immutable event describing:

- who caused the action;
- which command/action initiated it;
- which authority/version evaluated it;
- which resource changed;
- what immutable event represents the change.

## Conceptual event

Example only; not an approved schema:

```text
EconomicProvenanceEvent
  event_id
  player_id
  command_id
  source_action
  resource_type
  resource_id
  quantity_delta
  authority_version
  previous_state_digest
  resulting_state_digest
  created_at
```

## Non-goals

- No immediate production migration.
- No runtime behavior changes.
- No historical backfill.
- No automatic recovery of ambiguous historical states.
- No replacement of existing domain ledgers without review.

## Recommended v1 direction (pending approval)

Scope:

- critical economic actions, not every gameplay event;
- Inventory/resource consumption;
- capture economics;
- reward grants;
- trading/social transfers when introduced;
- currency or premium-value changes when introduced.

Generation model:

- domain transaction declares the economic intent;
- persistence boundary verifies and stores the immutable provenance event.

This avoids losing business context while preventing silent omissions from individual feature code.

Retention direction:

- hot operational storage for recent audit/support needs;
- archival strategy for long-term audit history.

## Open Human Owner decisions

Resolved decisions:

- Scope: critical economic actions.
- Authority boundary: domain intent plus persistence verification.
- Retention: hot storage plus archival strategy.
- XP/progression telemetry is handled by SPEC-030, not this ledger.

### 1. Scope

Should the ledger cover:

- only Inventory item changes;
- all player resources;
- rewards and capture economics;
- trading/social transfers?

### 2. Authority boundary

Should provenance be:

- generated by domain transactions only;
- generated by a persistence layer;
- generated by both with verification?

### 3. Retention

Define:

- permanent retention;
- archival strategy;
- query/index requirements.

### 4. Performance budget

Define acceptable cost for:

- write amplification;
- transaction latency;
- storage growth.

## Entry gate

Implementation requires:

1. Human Owner approval of this specification.
2. Architecture review.
3. Separate implementation task.
4. Migration plan only after runtime contract approval.
