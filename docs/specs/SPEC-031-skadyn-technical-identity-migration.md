# SPEC-031 — Skadyn Technical Identity and Compatibility Migration

Status: **APPROVED — Class A contract accepted by Human Owner on 2026-10-15; implementation, persistent schema/secret cutover, Git history and deployment each remain separately gated**

Owner: PM / Architecture Coordinator. Human Owner direction: stop using obsolete PokeNexus technical names as the project's current identity; **Skadyn Idle** is the internal product/code name, while **Skadyn Poke Idle** is the distinct, currently preferred visual wordmark for art studies. This specification is a migration proposal, not a change to the latter artwork decision or an approval of the current TASK-137 app copy.

Dependencies: current TASK-136 security/Alpha working tree must be reconciled before edits to its files; previous accepted ADR-004/ADR-006, SPEC-004, SPEC-017, SPEC-020/021, published data releases and migration ledger remain authoritative for historical data. Their forward amendments are scoped to the specifically approved changes in this contract.

## 1. Goal and canonical technical identity (approved target)

The **current-source namespace** should become `skadyn`, not `pokenexus`, across package/import names, the private monorepo package name, newly issued configuration variables, app/Worker identifiers, Docker/state names, database logical namespace and newly issued versioned protocol identifiers. Player-facing brand copy and visual lettering remain independently owned decisions. This refactor must not modify game balance, gameplay logic, Auth security guarantees, or irreversible historical content.

| Surface | Proposed new canonical name | Historical continuity requirement |
| --- | --- | --- |
| Private workspace root and 8 npm packages | `skadyn-idle`; `@skadyn/{api,web,realtime,database,game-core,game-data,game-protocol,game-types}` | Update every internal import/filter, Vite aliases, TS paths, CI, build scripts and generated `pnpm-lock.yaml` together; no npm publication. |
| PostgreSQL application schema, new local DB/user names | `skadyn`; e.g. `skadyn_local_alpha`, `skadyn_local_prealpha`, local role `skadyn` | Preserve AccountId, PlayerId, credentials, Sessions, Hunt/Inventory/Reward rows, constraints/FKs, immutable migrations/checksums and connection ownership. Renaming a physical PostgreSQL **database or role** is a separate quiesced operational step, not `ALTER SCHEMA`. `pokenexus_telemetry` is a separate TASK-132-owned schema. |
| Environment keys specific to this project | `SKADYN_*` (30 distinct `POKENEXUS_*` keys currently detected) | No insecure fallback or accidental startup with conflicting old/new values; secrets never printed. Generic `AUTH_*`, `ALPHA_*`, `HYPERDRIVE` are descriptive and should not be renamed for cosmetics. |
| Session and restricted cookies | `__Host-skadyn_session`, `__Host-skadyn_restricted` | Transitional dual-read/clear with deterministic precedence, browser cookie flags and no unintended session issuance/revocation. |
| Newly issued durable format and protocol IDs | `skadyn.*` with a **new explicit version or new authority identity** | Old `pokenexus.*` representations stay readable/verifiable under frozen legacy decoders until proven retired. No blind prefix rewrite of existing bytes. |
| Newly issued auth CSRF/cursor HMAC domains | New versioned `skadyn` domains **only after defined compat strategy** | Legacy proofs must verify under original domains; no cross-domain forgery or new-identity replay. **Genetics/individualization RNG-HMAC domains stay frozen** under current accepted rules. |
| New local state, containers, volumes, test fixtures, Worker names | `skadyn-*`, `skadyn.scope`, `%LOCALAPPDATA%/Skadyn/...` | Preserve and positively identify existing owner-scoped resources; do not orphan/delete old Docker volumes or local Alpha secrets. Worker/DO identity changes are deployment migrations, not string edits. |
| Repository directory / remote | Proposal for eventual `G:\skadyn-idle` and repository rename | Requires separately gated tool root/worktree/IDE/CI/remote reconfiguration; **do not move** the currently connected `G:\pokenexus-idle` workspace. |

## 2. Verified reasons a global replacement is unsafe

1. `packages/database/src/migrations.ts` hashes the **exact bytes** of each migration (`discoverMigrations`), checks a contiguous migration-ID/checksum ledger and records it in `pokenexus.schema_migrations`. SQL migrations 0001-0014 and the current TASK-136 0017 use the old schema. Editing old migration contents or renaming migration IDs breaks upgrades and ledger verification. The Alpha runner `scripts/alpha-migrate.mjs` deliberately selects 0001-0014 + 0017 and excludes TASK-132 migration 0016.
2. `packages/database/src/migrations.ts` currently bootstraps and writes the ledger under `pokenexus`. Merely adding `ALTER SCHEMA pokenexus RENAME TO skadyn` would cause same-transaction or next-run ledger access failures unless the migrator is redesigned and migration order/cases are tested first.
3. Exact IDs such as `pokenexus.solo-hunt-checkpoint.v1..v4`, `pokenexus.combat-presentation.v1/v2`, Hunt activity/pagination, capture/reward versions and Workbench `pokenexus.pokemon-move-workbench.v3` are consumed as serialized contracts. New `skadyn.*` IDs require new versions with **read-old/write-new** adapters, schema constraint changes where applicable, and deterministic historical replay checks. Existing downloaded files remain supported.
4. Published game-data manifests, normalizer identifiers and game-core production Move/rule artifacts have content-addressed hashes or immutable version pins. Their bytes are historical authority: never rewrite, rehash or republish them in place. Only independently versioned new publications may adopt the new namespace, with explicit paired-version integration. The existing `game-data-core-kanto-johto-v[1..5]` identifiers do not themselves contain the legacy brand and need not be changed.
5. `apps/api/src/auth/crypto.ts` uses `pokenexus-csrf-v1` as a live HMAC domain; `packages/game-core/src/encounter-individualization.ts` has separate fixed HMAC/authority domains; Hunt presentation cursors have their own signing domain. TASK-132 telemetry has SHA-256-based event identities derived from an old domain. Changing any namespace affects existing tokens, key IDs, RNG/Genetics, telemetry deduplication, checkpoint/cursor verification and may corrupt replay or reject old evidence. **The genetics/individualization domain, key-ID derivation and RNG outputs are frozen for the existing accepted rulesVersion, including new encounters.** Any future different domain would require a separately approved gameplay/authority version with deterministic vector review and applicable GSC consultation; this technical rename does **not** authorize it. Version compatibility must be proven, not assumed.
6. `apps/api/src/auth/http.ts` uses `__Host-pokenexus_session` and `__Host-pokenexus_restricted`. Renaming without reading/clearing old cookies can strand existing sessions and restricted flows. WebAuthn *RP ID and allowed Origins* are real hostname security boundaries (`localhost` in local Alpha), not cosmetic project names; changing a passkey RP ID requires a separately accepted real-domain migration, not this rename.
7. `scripts/local-alpha.ps1` and `scripts/local-prealpha.ps1` scope Docker ownership through `pokenexus.scope`, container/volume names, Windows state paths, exact database target names and secret/version labels. A blind rename may create a second state or leave old resources and encryption/authority material unrecoverable. TASK-136's unresolved potential Vite `/@fs/` secret leak stays blocking for **real credentials** regardless of rebranding.

## 3. Proposed sequence and isolation

**Stage A — namespace-only build refactor (TASK-139, Class B):** on an isolated source branch/worktree after the current TASK-136 source collision is reconciled, change root and all 8 private package names, references/imports, `package.json` scripts, TS paths, Vite aliases, Wrangler *local non-deployed package/config labels where safe*, CI, `.env.example`, `AGENTS.md`, `CLAUDE.md`, `.github/agents`, currently maintained `docs/agents`, agent skill descriptors/paths where owned and project-control dashboard generator text. Regenerate pnpm lockfile through Corepack. Preserve operational semantics of current agent skills and historic project decisions even when their headings are renamed. Do not yet change schema, live auth cookies, cryptographic strings, published manifests or persisted protocol bytes. Verify full workspace, Worker dry-runs and imports. Keep any preexisting release/DO worker name frozen until external migration authorization.

**Stage B — legacy resource discovery and safe operators (TASK-140, Class A):** inventory existing local Alpha/Pre-alpha containers, DBs, owner labels, persisted secrets, session/cookie and publication authority, with hashes/row counts and an independently checked restore snapshot. Define explicit owner-scoped adoption/opt-in migration of old names to Skadyn; zero automatic `docker volume rm`, DB recreation, secret rotation or provider activation. New env variables can replace old in one coordinated launcher/API switch only when every consumer changes; transitional alias handling must fail closed on conflicting values and preserve absolute loopback/domain guards.

**Environment cutover rule:** for each project key define the mechanical mapping `POKENEXUS_<suffix>` → `SKADYN_<same suffix>` and inventory all observed 30 keys (see below). Under the pre-cutover, explicit legacy-operator **read/adoption** tool, `old only` may be read without logging a value; `new only` is canonical; `both present` must fail closed **even when values match** for DB URLs, bearer/secrets and operational authority. The new production/local launcher accepts **new only** once cut over; no silent fallback to old names. Missing required config fails closed. Test every consumer, especially `scripts/alpha-migrate.mjs`, `packages/database/src/migration-cli.ts`, `packages/database/scripts/issue-alpha-invite.mjs`, PowerShell launchers, API local runtime and both Vite modes, against missing, old-only, new-only and dual-set cases. Never create new Skadyn state/volumes if a legacy resource for the **same verified checkout** exists but has not been explicitly adopted. An actual provider secret, bearer or database connection URL must never be printed during discovery.

**Observed key matrix (old prefix shown for audit; new prefix is `SKADYN_`):**

| Consumer family | Suffixes to migrate as one validated configuration set |
| --- | --- |
| Alpha / DB / web routing | `ALPHA_API_TARGET`, `ALPHA_DB_URL`, `DIRECT_DATABASE_URL`, `TEST_DATABASE_URL`, `LOCAL_API_TARGET`, `LOCAL_DATABASE_URL`, `LOCAL_SESSION_BEARER`, `LOCAL_WEB_PORT` |
| Local game/bootstrap/authority | `LOCAL_AUTHORITY_KEY_ID`, `LOCAL_AUTHORITY_VERSION`, `LOCAL_BOOTSTRAP`, `LOCAL_BOOTSTRAP_CURSOR_KEY`, `LOCAL_GAME_DATA_BASE_URL`, `LOCAL_GENETIC_PROFILE_RELEASES`, `LOCAL_INDIVIDUALIZATION_AUTHORITY_RELEASES`, `LOCAL_INDIVIDUALIZATION_AUTHORITY_VERSION`, `LOCAL_PLAYER_A`, `LOCAL_PLAYER_B`, `LOCAL_STARTER_A`, `LOCAL_STARTER_B`, `LOCAL_STARTER_CONVERSION` |
| Replay/operations/data publication | `AUTHORED_ARTIFACTS`, `CONVERSION_ACTION`, `CONVERSION_APPLY_AUTHORIZATION`, `CONVERSION_PLAN`, `CONVERSION_PLAN_SHA256`, `GAME_DATA_BASE`, `LIVE_INGESTION`, `LIVE_INGESTION_ROOT`, `RUN_PRESENTATION_BENCHMARK` |

**Legacy resource exception:** operator code under a narrowly identified `scripts/compat/` (or named equivalent) may intentionally contain original `pokenexus.scope`, persisted Alpha/Pre-alpha state-version strings and old Docker/container/path names for *read-only discovery, ownership checks and copy-forward adoption*. This compatibility code is never a normal writer of new PokeNexus artifacts. Record an allowlist and negative tests; Stage F's no-legacy-new-operator-script gate excludes **only** that reviewed legacy adapter.

Include `renderer-preference.ts` localStorage, Hunt pending-command/sessionStorage and pending Team-create intents in browser storage migration. Read an old key only with the original session/player fingerprint validation, promote to one canonical new key without duplicate authoritative commands, clear it only after the new state is durably known, and reject conflicting/foreign/corrupt old/new entries. Never drop a pending command merely to remove a storage name.

**Browser migration discovery set:** `apps/web/src/renderer-preference.ts` (`localStorage`), `apps/web/src/hunt-command-store.ts`, `apps/web/src/hunt-pages.tsx`, `apps/web/src/team-create-intent.ts` (`sessionStorage`). Tests must cover missing storage, malformed v1, old/new conflict, same-key idempotent read, different Player/session fingerprint, pending unresolved commands, a browser reload and multi-tab contention. Promote the key only after server reconciliation determines a single authoritative outstanding command; never dual-submit on both names.

**Stage C — database cutover:** keep historical SQL files **bit-for-bit unchanged**. Introduce an additive migration (provisional `0018`, order subject to TASK-132/136 ledger reconciliation) that migrates the existing schema identity transactionally, keeps all table OIDs/FKs/data, adapts function bodies/search paths as needed, and records a ledger entry in the correct physical schema after rename. Migrate the `runMigrations` bootstrap/query/insert/lock logic so it detects exactly one source/target schema, verifies unchanged historical hashes and the Alpha subset 0001-0014+0017, fails closed on ambiguous double schemas, and works for both fresh DB and already-used Alpha/Pre-alpha DB. **Do not serve traffic between schema rename and switching the entire SQL consumer fleet to the matching `skadyn`-qualified build.** The new SQL consumer, the ledger-aware migration runner and reverse-compatible rollback artifacts must be built and tested *before* downtime; only a quiesced coordinated cutover is eligible. Coordinate whether and how to treat the separate TASK-132 telemetry schema; never apply its 0016 migration during Alpha implicitly. Test fail/retry/rollback and independently checked restore. Never test against the preserved shared DB.

**Required cutover state machine:** (1) identify exactly one schema/ledger and valid ownership, snapshot/restorable backup, historical digest/row count/function and ACL baseline; (2) stop API/Worker/background SQL access, wait for active transactions to end, take the **unchanged existing migration advisory lock**; (3) in a controlled transaction apply the additive schema rename, update nonautomatic qualified function/search-path/grant references and put the new migration ledger entry under the correctly renamed ledger; (4) while traffic is still halted, atomically install a matched SQL-consuming application/migrator and inspect all table IDs/FKs/constraints/ledger SHA-256s; (5) restart services only if exact health/auth/replay probes pass; otherwise stay stopped and execute the *tested* reverse schema/ledger migration or recover the snapshot. No mixed old-SQL/new-schema live period is allowed. A freshly provisioned database executes historical pinned migrations once before the additive rename; the runner's final ledger insert must target the post-rename schema. Later runs detect the existing `skadyn` ledger without creating a second empty `pokenexus` ledger. The TASK-136 selective Alpha runner adds this migration to its curated list without introducing excluded 0016; never invoke the generic all-migration CLI against that Alpha database. An optional TASK-132 telemetry schema migration must be coordinated under its own owner and immutable event/dedup proof.

The accepted SPEC-004's historical `pokenexus`-qualified rule needs an explicit **forward amendment** when this contract is approved, not an in-place alteration of old accepted SQL/spec evidence. Physical local database/user name migration requires closing active connections, verifying exact owned volume, implementing an explicit `ALTER DATABASE`/role/connection-string transition or a restore into a new named DB, and testing reattachment without duplicating data. This is separate from schema rename. Never infer a production database rename from the local example. Historical functions/grants/triggers must be inspected, not assumed to rewrite qualified source text on schema rename.

**Telemetry ownership decision:** target `skadyn_telemetry` for the TASK-132 private schema **only after its own migration branch/0016 status and owner are reconciled**. Historical `0016_gameplay_balance_telemetry.sql` remains immutable once applied; an additive telemetry-specific migration must safely rename the schema, preserve events and existing `stableTelemetryUuid` results under their accepted v1 domain, and update consumers behind a coordinated writer stop/go. On Alpha, 0016 remains excluded and no telemetry schema should be created just to complete branding. An unmerged/unapplied 0016 or historical telemetry schema is an explicitly documented outstanding technical-identity gate, **not** grounds for silent rewrite by TASK-140 or claiming total cleanup before that gate completes.

**Stage D — auth and browser identity transition:** preserve AccountId, WebAuthn `userHandle`/credentialId, challenge binding, RP ID, exact Origins, flags `Secure`, `HttpOnly`, host-only, `Path=/`, SameSite and CSRF requirements. During a bounded migration window, accept either old or new cookie name **only after unambiguous principal validation**: a present invalid new cookie must never fall back to a good old cookie; different valid principals conflict and must fail closed. New cookie issuance expires the old name with matching scope attributes and supports multiple `Set-Cookie` headers; sign-out/revoke clears both. Existing sessions remain subject to their **original durable absolute expiry (at most 30 days) and inactivity expiry (7 days)**; do not mint a new 30-day lifetime on a rename. Restricted flows still have their original 15-minute lifetime. Reusing an existing bearer alias avoids DB rotation but requires proof against downgrade; rotating bearers instead requires atomic DB/CAS and concurrent-tab recovery. For CSRF/HMAC, retain legacy validation only as long as needed for already-issued proofs; produce purpose-bound versioned new tokens, check each under its correct legacy/new source domain with constant-time comparison, and do not authorize old CSRF under a promoted new-cookie flow. Confirm `/auth/session` and `/auth/restricted/session` send `no-store` and synchronize token promotion. Prove sign-in/logout/recovery/current sessions with real-shaped test records and two independent browser profiles. No secret logs or bearer in URL. Any RP domain or public deployment change is separately gated. Rollback **after** new cookies/tokens have been issued must use a prior dual-reader-compatible release, not an old-only build.

**Required auth state machine (default decision):** reuse the **same validated existing random bearer** during a cookie-name-only migration (no DB digest rewrite, no token lifetime extension). For session and restricted cookies independently: `new only` → verify the new bearer and purpose, issue/verify only the corresponding purpose-separated `skadyn.auth.csrf.v2` token; `old only` → verify the old bearer/securityEpoch and original `pokenexus-csrf-v1` proof, with no implicit cookie promotion on mutation routes; `both present` → accept only if both raw bearers are byte-identical and refer to the same verified server principal, otherwise fail closed, including new-invalid/old-valid. **When both match, the NEW cookie wins: only its v2 CSRF is valid; the response expires the redundant old cookie. A stale v1-only mutation must fail CSRF without falling back to legacy authorization, and the client must refresh its authenticated session first.** **Only** GET `/auth/session` or `/auth/restricted/session` with a valid old principal may promote it by returning a canonical new cookie reusing the bearer, an old-name `Max-Age=0` deletion cookie and a corresponding new CSRF token in the same `no-store` response. New sign-in/registration flows write only new names/tokens. The cookie expiry on promotion must be bounded by the actual DB-stored original `absoluteExpiresAt` and current inactivity/purpose TTL; obtaining that bound requires a verified repository/application query since the present `AuthSessionPrincipal` does not expose it. Logout/revoke/delete always clears both names and server authority; no CSRF v1 acceptance on a promoted new-only request. Legacy cookie acceptance is bounded to at least the original maximum existing session lifetime (30 days from last legacy issuance), and restricted-flow compatibility 15 minutes; retirement requires explicit proof that the time window elapsed and no legacy issuance remains. Prove Hono's *multiple* `Set-Cookie` transport and concurrent-tab state reconciliation. No new key is silently generated or old security secret rotated as part of this alias migration.

**CSRF v2 exact cryptographic bytes:** for the **unchanged existing** `csrfKey` and canonical lowercase-hyphenated UUID `bindingId`, derive `base64url_unpadded(HMAC_SHA256(utf8(csrfKey), utf8("skadyn.auth.csrf.v2\u0000" + purpose + "\u0000" + bindingId)))`, where `purpose` is the exact ASCII enum `session` or `restricted`; never accept a third purpose or ambiguous encoding. Keep v1 bytes/verifier frozen and dispatch verification strictly by the validated cookie cohort above, with constant-time comparison. Nonsecret golden conformance vector: key `test-csrf-key-material-at-least-32-bytes`, UUID `018f47f0-4f7b-7d1f-8f5a-6b312f81bbad`, `session` → `moSgoFsKwySwMKmIBR1ruy3uIqqudOnc__wve7xk2l4`, `restricted` → `HprE7tBP9SfUwVlgZc5Zc20Qcp8UNOrPLBBoVJYsle4`. Reject a token for the other purpose. This format is approved **as part of SPEC-031**, but its implementation and activation remain separately gated; the current CSRF v1 implementation stays unchanged.

**Hard precondition — preserve pending Team-create identity across CSRF-domain change:** `apps/web/src/team-create-intent.ts` stores `sessionFingerprint = SHA256(csrfToken)` in `sessionStorage`, with the idempotency UUID; changing CSRF v1 → v2 for the SAME DB session makes the record look like another session, blocking/resuggesting discard. Do **not** silently discard or issue a different command. First deploy reader/client compatibility for legacy pending intents while server cookie+CSRF output remains unchanged. Then add an authenticated, `no-store`, same-origin session response migration proof carrying **only** `SHA256(legacyCsrfV1ForThisSameVerifiedSession)` (not the raw legacy token or session bearer) alongside the new v2 CSRF; the old proof is a browser-local rebind hint, **never** accepted for auth or mutations. During bounded migration it must remain available to authenticated clients on both old and already-promoted cookie names, so another tab or an interrupted reload can recover. Before rendering mutation-capable Team UI, the new ClientSessionProvider/TeamCreateIntentStore validates legacy record UUID/format and equality to that authenticated migration proof, then promotes the **same UUID** to the new storage key/fingerprint (`SHA256(newCsrfV2)`) with read-back verification. Remove the old key only after verified new storage; as `sessionStorage` cannot transact two keys atomically, a crash between these writes may leave both. On retry, reconcile two matching correctly bound records with the SAME UUID, but fail closed if the keys, session markers or command UUIDs differ. If storage fails, retain the original for retry and refuse any new Team-create command. Different account/session or forged marker never rebinds; sign-out still clears private caches per existing policy. Continue replaying the same UUID through the authoritative server idempotency path if the prior response was lost. Test login reload, in-flight/lost-response success, both-cookie transition, two tabs, old/new key conflict, crash-between-storage-writes, changed account, duplicate create prevention and user-initiated discard. If this preparatory client/server bridge cannot be proven, **do not activate cookie or CSRF v2**; freezing the old proof until safe migration is preferable to a broken Team-create contract.

**Stage E — immutable protocol/data evolution:** preserve old decoders and frozen test vectors; new writes use versioned `skadyn.*` identifiers only for compatible *new format families* where consumer/data/DB CHECK compatibility is proven and accepted. **Do not rewrite or re-label the existing game-core Genetics/individualization HMAC, rule identities, item identities or RNG semantics**, even for newly created Pokémon, until a separately approved rule/content/authority version explicitly covers them; current stable values may remain behind `legacy` or `accepted-v1` constants. Test legacy checkpoint and Hunt replay, inventory/item IDs, deterministic Genetics authority, signed continuation cursors, existing signed/history assets, workspace download/import, no double grants, offline recovery and old/current data-pair startup. Never dual-write authoritative reward/Hunt/telemetry ledgers; a new deterministic telemetry-ID algorithm must be separately versioned/dedup-safe. No re-signing historical evidence or retroactive rewrite of immutable publications. Old tokens may expire normally under their original TTL; replay data survives indefinitely where specified. Any changes to previously accepted SPEC-002/004/017 or ADR-006 contracts must be recorded as **forward amendments** under Class A.

**Item IDs are frozen for current publication:** `pokenexus:item:poke-ball:v1`, basic Potion and Revive ID families identify durable owned Inventory and embedded published content, not free text. They remain authoritative under current game-data v5 for *both old and new operations*. There is **no automatic minting of `skadyn:item:*` aliases**. If a later approved immutable publication adopts new IDs, require a reviewed one-to-one mapping and a single transactional conversion that keeps ownership, quantity, outstanding policy references, reward ledgers, capture/replay provenance and idempotency identities coherent. No split inventory, double rewards or double debits may result. A similar rule applies to rulesVersion and CombatPresentation source authority.

**Reader-first activation barrier:** before any new `skadyn.*` wire/persisted writer is enabled, extend and independently validate old+new API/client/DB read unions and any database CHECK constraints, then prove a version-negotiated old-client grace path or intentionally end old-client sessions at a separately approved cutover. `apps/web/src/hunt-api.ts` currently rejects unknown Hunt activity/page versions; the public presentation DB migration currently restricts schemas to known v1/v2 strings. Therefore new-version writes **cannot** start while old-only clients, old-only API workers or old DB constraints might consume them. New writers remain feature-disabled until coordinated activation. Rollback after activation must be to the last **dual-reader** build, never an old-only binary unable to interpret new durable bytes. Workbench exports may adopt a later `skadyn.pokemon-move-workbench.v4` only with strict old v3 import compatibility, new v4 round-trip and corruption/hash rejection tests; currently changed download **filename** is not a payload version change.

**Stage F — verification and cleanup:** inventory using a source-and-output audit that treats new runtime/current docs as Skadyn-only, with explicit allowlisted historical SQL, published content, saved-version fixtures, provenance hashes, small read-only compatibility decoders, the **one-time audited schema/ledger bridge migration that necessarily names its old source** and the **reviewed legacy-only operator resource adapter** in Stage B. No `pokenexus` in current package/import names, currently issued env/cookies, normal new steady-state SQL consumers, normal operator scripts, CI, ordinary logs or new docs. Historical name literals in *immutable records, one-time source-to-target migration SQL, legacy resource discovery or compatibility readers* are a correct technical contract, not unfinished branding, and must be explicitly enumerated rather than hidden by a broad ignored directory. Remove aliases only with expiry/data proof and a separate Human gate. Rename the connected repository folder and any Cloudflare deployed Worker/DO resources only with separate migration/runbook and external authority.

## 4. Acceptance matrix / non-regressions

- **Workspace:** exact packages/imports/scripts/CI/TS/Vite resolve `@skadyn/*`; fresh dependency install/lockfile reproducible; workspace tests/lint/build/typecheck pass; no stale `@pokenexus/*` import outside frozen historical examples.
- **Migrations:** disposable PostgreSQL 17 fresh install, old full production-compatible prefix, Alpha selected prefix and optional 0016 telemetry scenario all pass checksum/ledger/idempotency tests; old AccountId and every durable Player/Team/Pokémon/Inventory/Hunt/Auth row are byte-equivalent; rollback exercise and cold restart succeed. Never run new migrations on existing persistent DB without distinct Human approval and backup evidence.
- **Auth:** real, independent browser profiles preserve existing passkeys; discoverable sign-in, session renewal and rotation, CSRF/restricted flows, logout, old/new cookie precedence, Origin and CORS fail-closed, no Domain attr or cross-origin relaxation; no silent mass logout. No real provider key until separate TASK-136 secret-exposure P1 is fixed and re-gated.
- **Deterministic data:** fixture old JSON payloads and checkpoints replay byte-exact under original versions; new version round-trips, offline and Hunt cursor boundaries, signed old values and failed duplicate transactions covered. Pinned game-data/production move hashes and generated artifacts unchanged unless a separate immutable new publication is accepted.
- **Operations:** local resource discovery, state/provenance and rollback preserve owner ACL and secrets; never adopt another checkout's Docker volume; `Status` and `Stop` ownership checks pass. Deployed runtime/API/DO identity migration has a separate release plan.
- **Governance:** independent QA plus Independent Auditor pre/post Class-A, Human approval of this contract before READY/implementation, Human approval before history and database/production cutover; no overlap with dirty current TASK-136/132 writers. The scoped Class-B TASK-137 approval does **not** authorize these changes.

## 5. Approved technical decisions and remaining execution gates

1. Adopt the canonical tokens in section 1 (`@skadyn/*`, `SKADYN_*`, `skadyn`, `__Host-skadyn_*`, new-version `skadyn.*`) as the migration **target**. Preserve compatibility for existing accounts/data by default; never reset the DB to remove a name.
2. Require immutable historical SQL/publications and legacy read adapters even if the source contains the old name in an isolated compatibility area; there is no safe zero-old-byte promise without declaring data/history loss.
3. Stage migration behind approved security/database contract, with two implementation workstreams and explicit proof before deleting old aliases.
4. Defer renaming the physical repository root, Git remote and any deployed Cloudflare resource until their own tooling and release preparations are authorized.
